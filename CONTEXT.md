# 📋 TaskBoard — Контекст и Документация Проекта

Данный документ является единым источником правды (Single Source of Truth) по архитектуре, функционалу и текущему состоянию проекта **TaskBoard**.

---

## 🛠 1. Стек Технологий и Архитектура

- **Фреймворк**: Next.js (App Router, JavaScript, CSS Variables без Tailwind).
- **База Данных**: Supabase (изолированные таблицы `tb_` для безопасной работы в общей БД).
- **Авторизация**: Кастомная автономная система логин/пароль через таблицу `tb_profiles` (без встроенного Supabase Auth/Email).
- **Telegram Уведомления**: Интеграция с Telegram Bot API для отправки анонимных отчетов в супергруппу компании.

---

## 🗄 2. Структура Таблиц Базы Данных (Supabase SQL)

### `tb_profiles` — Профили пользователей
- `id` (UUID PRIMARY KEY)
- `username` (TEXT UNIQUE) — Логин для входа
- `password` (TEXT) — Пароль
- `name` (TEXT) — Имя и Фамилия
- `avatar` (TEXT) — Эмодзи-аватар
- `color` (TEXT) — Цвет профиля
- `role` (TEXT: `employee` | `manager` | `admin`)
- `is_admin` (BOOLEAN)

### `tb_tasks` — Задачи
- `id` (UUID PRIMARY KEY)
- `task_number` (SERIAL) — Человеческий порядковый номер (`№1`, `№2`...)
- `title` (TEXT)
- `description` (TEXT)
- `status` (`new` | `in_progress` | `stopped` | `review` | `done`)
- `progress` (INTEGER: 0, 25, 50, 75, 100)
- `priority` (`low` | `medium` | `high` | `critical`)
- `created_by` (UUID) — Постановщик задачи. Выбирается в форме («📌 Кто поставил задачу»), по умолчанию — текущий пользователь. Доступно **всем ролям**: сотрудник, которому поручили работу устно, заводит задачу сам и указывает, кто её поручил — иначе выглядело бы, будто он сам нашёл себе работу
- `assigned_to` (UUID) — Первичный исполнитель
- `assignees` (TEXT[]) — Массив всех исполнителей
- `responsible_id` (UUID) — Ответственное лицо за прогресс и статус
- `tags` (TEXT[]) — Теги задачи
- `stop_reason` (TEXT)
- `deadline` (DATE)
- `pinned` (BOOLEAN)
- `difficulty` (INTEGER 1–10, NULL) — Сложность задачи для рейтинга. `NULL` = руководитель ещё не оценил.
- `completed_at` (TIMESTAMPTZ) — Дата фактического закрытия. Пишется **один раз** при переходе в `done`, обнуляется при возврате в работу.

> ⚠️ Для «когда задача была выполнена» использовать **только `completed_at`**, не `updated_at`. `updated_at` меняется при любом редактировании — в том числе когда руководитель задним числом проставляет сложность закрытой задаче.

- `difficulty` (INT 1–10) — Сложность, ставит только руководитель. `NULL` = не оценена
- `quality` (INT 1–5) — Качество работы, ставит руководитель при приёмке
- `assignee_shares` (JSONB) — Доли в командной задаче: `{"user_id": 60, "user_id": 40}`
- `submitted_at` (TIMESTAMPTZ) — Момент сдачи на проверку
- `completed_at` (TIMESTAMPTZ) — Момент приёмки руководителем

### `tb_comments` — Комментарии к задачам
### `tb_task_history` — История изменений
### `tb_notifications` — Внутренние уведомления

## 👥 3. Роли и Права Доступа

1. **👨‍💻 Обычный сотрудник (`employee`)**:
   - Видит задачи, где он является создателем, одним из исполнителей или ответственным.
   - 🔒 **Ограничение прав**: Может оставлять комментарии и общаться в чате задачи. Менять статус и проценты прогресса разрешено **только если сотрудник назначен Ответственным лицо (`responsible_id`)**.
   - Участвует в **🏆 Рейтинге сотрудников** (сам его не видит).
2. **🧑‍💼 Руководитель (`manager`)**:
   - Видит все задачи всех сотрудников компании и полную аналитику.
   - Имеет доступ к модальному окну **`👥 Команда`** и фильтрации задач по сотрудникам.
   - ⚡ **Выставляет сложность (1–10) и качество (1–5)** — в любой момент, включая закрытые задачи.
   - Принимает сданные на проверку задачи и задаёт доли в командных задачах.
   - Видит страницу рейтинга и **сам в нём участвует** — у руководителей есть свои задачи.
3. **👑 Администратор (`admin`)**:
   - Полный доступ к системе + доступ к **`⚙️ Панели администратора`**.
   - Регистрация новых сотрудников, управление ролями, удаление пользователей.
   - Видит страницу рейтинга `/dashboard/rating` (как и `manager`). В рейтинге **не участвует**.

## 📢 4. Telegram Уведомления и Конфиденциальность

Вся логика — в `lib/telegram.js`, точка входа `sendTelegramNotification(type, payload)`.
Уведомления идут по **двум независимым каналам** с разным уровнем детализации.

### 📣 Канал 1 — Общая группа (кратко)
- **Группа Telegram**: Супергруппа компании (`-1004498774399`).
- **🔒 Политика Конфиденциальности**:
  - Названия и описание задач **НЕ публикуются в Telegram-группе**, чтобы другие сотрудники не читали чужие конфиденциальные поручения.
- **Форматы уведомлений**:
  - 📌 **Новая задача**: `📌 Новая задача №1`, создатель, исполнители, ответственный.
  - 💬 **Комментарий**: `💬 Новый комментарий к задаче №1`, автор.
  - ✅ **Завершение**: `✅ Задача №1 была завершена!`, ответственный, время выполнения (`⏱ X ч Y мин`).

### 👑 Канал 2 — Личные сообщения руководителям (полная информация)
- **Получатели**: константа `MANAGER_CHAT_IDS` в `lib/telegram.js` — личные Telegram chat_id руководителей, **захардкожены** (намеренно не в `.env`, чтобы не заводить переменные в Vercel).
- **⚠️ Важно**: в ЛС названия и описания **публикуются полностью** — ограничение конфиденциальности действует только для общей группы.
- **События с полным ЛС** (`managerDmText`):
  - 📌 **Создание задачи**: название, описание, срок, приоритет, кто назначил, исполнители, ответственный.
  - ✅ **Завершение задачи**: название, описание, срок, кто создал, исполнители, ответственный, время выполнения.
- Комментарии в ЛС **не дублируются** — только в группу.

## 🏆 5. Рейтинг сотрудников (для премирования)

Логика — в `lib/rating.js`, страница — `/dashboard/rating` (**видна ролям `manager` и `admin`**, обычным сотрудникам — нет).

- В списке показывается **топ-10** (константа `TOP_LIMIT`), остальные скрыты со счётчиком.
- Вкладки: общий балл, количество задач, сложность, сроки, качество. Каждая пересортировывает тот же список; при равенстве порядок разрешается по общему баллу.

- **Помесячный**, каждый месяц счёт начинается заново.
- **Считается на лету** из `tb_tasks`, без сохранённых снапшотов. Это обязательное требование: руководитель может изменить сложность задачи за прошлый месяц, и рейтинг того месяца должен пересчитаться. Не заводить таблицу с посчитанными результатами.
- **Участники**: сотрудники и руководители (`employee` + `manager`) — руководители тоже ведут свои задачи. Исключён только аккаунт админа.
- **Сложность** ставит только `manager`/`admin`, в любой момент, включая уже закрытые задачи. Без оценки задача даёт **0 баллов** (срок и качество тоже не начисляются).

### Приёмка работы
Сотрудник **не закрывает задачу сам**: он жмёт «🔍 Сдать на проверку» (статус `review`), а руководитель принимает («✅ Принять» → `done`) или возвращает на доработку. Кнопка «Принять» доступна только `manager`/`admin`.

### Формула — только сложение, никаких множителей
```
баллы за задачу = сложность + балл за срок + качество

сдал в дедлайн   → +1
без дедлайна     →  0
просрочка        → −1 за каждые ПОЛНЫЕ 10 дней

  1–9 дней  →  0   (неполный период не считается)
  10–19 дн  → −1
  20–29 дн  → −2
  30–39 дн  → −3   и так далее

итог за месяц = сумма баллов по всем принятым задачам
```
Пример: сложность 6, сдана в срок, качество 5 → **6 + 1 + 5 = 12 баллов**.

### Ключевые правила
- **Считаются только принятые задачи.** Задача в статусе `review` баллов не даёт и числится незакрытой.
- **Срок проверяется по `submitted_at`** (дата сдачи), а не по дате приёмки — медленная проверка руководителем не лишает сотрудника балла за срок.
- **Месяц определяется по дате сдачи.** Сдал 31 августа, приняли 2 сентября → баллы уходят в август.
- Дедлайн — календарная дата: сдача в любое время **дня дедлайна** считается «в срок».
- **Командные задачи** делятся по `assignee_shares` (`{"user_id": 60, ...}`). Проценты нормализуются, поэтому 6/4 работает так же, как 60/40. Без долей баллы делятся **поровну** между исполнителями.
- Доля закрытых показывается в строке сотрудника, но **на баллы не влияет**.
- Все коэффициенты — в константе `RATING_CONFIG` в начале `lib/rating.js`, менять формулу только там.
- Клик по строке рейтинга открывает разбор по задачам (`components/RatingModal/EmployeeRatingModal.js`).

## 📊 6. Аналитика (`/dashboard/analytics`)

- **Данные общие для всех ролей.** Страница грузит задачи напрямую из `tb_tasks`, а не через `useTasks` — тот сужает список до задач самого пользователя, из-за чего аналитика превращалась в личный отчёт вместо картины по компании.
- Исключение: блок «⚠️ Требует внимания» (отстающий сотрудник) виден только `manager`/`admin`.

- **Период**: селектор «За всё время» + список месяцев, у которых есть данные. В месяц попадает задача, **созданная или завершённая** в нём, — поэтому переходящие задачи видны в обоих месяцах.
- **Статусы задач**: пончик + легенда с количеством и **процентом по каждому статусу**, включая `review`.
- **Общий прогресс**: доля задач `done` от всех видимых, с подписью «Выполнено N из M».
- **⚠️ Требует внимания**: сотрудник с самым низким процентом выполнения (при равенстве — с бо́льшим числом незакрытых; учитываются только те, у кого от 2 задач). Показывает разбивку по всем статусам, число просроченных и всего назначенных.
- ⚠️ **Видимость зависит от роли**: `manager`/`admin` видят все задачи компании, сотрудник — только свои. Поэтому одна и та же карточка показывает разным людям разные цифры.

## 🧭 7. UX-соглашения

- **Escape закрывает окна**, причём только верхнее: хук `useModalBehavior` в `hooks/useModalBehavior.js` ведёт общий стек открытых модалок. Все модалки обязаны использовать его, а не свой обработчик — иначе Escape закроет и соседнее окно. Он же блокирует прокрутку фона.
- **Прогресс и статус связаны** (`updateProgress` в `hooks/useTasks.js`): любой прогресс на новой задаче переводит её «В работе», 100% — «На рассмотрении». Переход идёт через `changeStatus`, чтобы проставился `submitted_at` и ушло уведомление руководителям. Страницы обязаны звать `updateProgress`, а не `updateTask({ progress })` напрямую.
- **Дедлайн задаётся не при создании**: срок ставит себе исполнитель в карточке задачи, руководитель может его изменить (`setDeadline`).
- **Поиск понимает номер задачи**: `12` или `№12` ищет по `task_number`, остальное — по названию, описанию и тегам.

- **Уведомления вместо `alert()`**: `showToast(message, type)` из `components/UI/Toast.js` (`success` | `error` | `info`). Работает через window-событие `tb-toast`, поэтому вызывается откуда угодно без прокидывания пропсов. Хост подключён один раз в `app/dashboard/layout.js`. **Не использовать `alert()`** — он блокирует интерфейс.
- **Необратимые действия только через подтверждение**: `components/UI/ConfirmDialog.js`. Удаление задачи обязательно проходит через него — на телефоне «🗑 Удалить» стоит рядом с «Изменить», и раньше один случайный тап уничтожал задачу вместе с комментариями и историей.
- **Сроки задачи показываются полностью**: «дано N дн» (от постановки до дедлайна), «Выполнено за N дн из N дн» и «просрочка N дн». Считает `getTaskTiming()` в `lib/utils.js` — по `submitted_at`, чтобы медленная приёмка не искажала цифры.
- **Защита от дублей**: кнопка сохранения формы блокируется на время запроса и показывает «Сохранение…».
- **Фильтры на доске свёрнуты на телефоне** под кнопкой «Фильтры и сортировка»; на десктопе видны всегда.
- **Каждое действие даёт отклик**: создание и сохранение задачи, смена статуса, сдача на проверку, приёмка, удаление — всё подтверждается тостом; ошибки БД показываются текстом, а не молча уходят в консоль.

## 🏷 8. Особенности UI и Фильтров

- **Человеческая нумерация**: Задачи отображаются с номерами `№1`, `№2`, `№3` на карточках, в модальных окнах и в Telegram.
- **Теги**:
  - Главный тег выводится в правом верхнем углу карточки напротив приоритета.
  - Список тегов отображается под описанием.
  - Выпадающий фильтр `🏷️ Все теги` над Канбан-доской.
- **Завершённые задачи на карточке**:
  - У задач со статусом `done` счётчик дедлайна **не показывается** (иначе готовая задача продолжала бы висеть с «Просрочено»).
  - Вместо него выводится `✅ Выполнено за X`, где X = `updated_at − created_at` (`TaskCard.js`).
- **Мобильная версия**:
  - Нижняя навигационная панель (`mobile-bottom-nav`), до 6 пунктов, с учётом `safe-area-inset` на iPhone.
  - Быстрые плашки колонок доски (`mobile-board-pills`).
  - Плавающая кнопка `+ Задача` (`mobile-fab-btn`); дублирующая кнопка в тулбаре на мобильном скрыта.
  - ⚠️ **Все поля ввода на мобильном — минимум `16px`.** Меньший размер заставляет iOS Safari зумить страницу при фокусе, из-за чего вёрстка «слетает». Не понижать.
  - Модалка задачи: шапка липкая и в столбик, кнопки оценок (сложность 1–10, качество 1–5, прогресс) — сетка `.score-btn-grid` по 5 в ряд, строки `.detail-row` вертикальные.
  - Рейтинг: строка `.rating-row` переносит баллы в отдельную нижнюю строку.

## 📄 9. Файлы Скриптов и Настроек
- `supabase-setup.sql` — Полная структура БД для выполнения в Supabase SQL Editor.
- `.env.local` — Переменные окружения (`SUPABASE_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).
- `lib/utils.js` — Общие хелперы: `formatDuration` (мс → `X дн Y ч` / `X ч Y мин`), `formatRelativeTime`, `getDeadlineStatus`, `getPriorityLabel`, `getStatusLabel`, `normalizeTags`, `getTaskNumber`.
- `lib/telegram.js` — Отправка уведомлений. Импортирует `formatDuration` и `getPriorityLabel` из `lib/utils.js`.

### ⚠️ Приоритет настроек Telegram
`getTelegramSettings()` берёт токен и chat_id в следующем порядке:
1. `localStorage.tb_telegram_settings` (**перебивает всё остальное**),
2. `process.env.NEXT_PUBLIC_TELEGRAM_*`,
3. Захардкоженные `DEFAULT_BOT_TOKEN` / `DEFAULT_CHAT_ID`.

**Типичная поломка**: если в `localStorage` лежит старый/битый `botToken` — уведомления молча перестают отправляться, т.к. фолбэк на дефолт срабатывает только когда значение пустое. Лечится в консоли браузера:
`localStorage.removeItem('tb_telegram_settings')`
